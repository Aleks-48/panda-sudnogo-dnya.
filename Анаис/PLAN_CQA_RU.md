# План решения CQA Hackathon

Источник требований: CQA_Hackathon_Student_Guide_v3 1.pdf, 4 страницы. План подготовлен по руководству; отдельный PDF чек-листа не предоставлен. DEV впоследствии скачан и проверен, текущий статус приведён в конце. Указанные ниже архитектура, распределение времени и дополнительные проверки — рекомендации, а не дополнительные требования организаторов.

## 1. Что требуется получить

За 24 часа создать работающий прототип Conversation Quality Analytics: пользователь настраивает чек-лист, загружает диалог, получает оценку работы оператора с доказательствами, подаёт апелляцию, а проверяющий принимает решение. После решения итог пересчитывается, исходная оценка сохраняется.

Обязательные результаты сдачи:
- Интерфейс на HTML, CSS и JavaScript, структура которого допускает последующую адаптацию в HTML-компонент Dynamics 365. Полная интеграция в Dynamics в руководстве не требуется.
- Сервис оценки и сохранение конфигурации и результатов; конкретные модель, сервер и хранилище выбирает команда.
- Открытый Git-репозиторий; ссылка заранее отправлена организаторам командой.
- README с понятным запуском. Если модель платная — её название и примерная стоимость одной оценки с учётом всех вызовов.
- Последний коммит зафиксирован к T+24 часа; проверяется именно эта версия.
- Демонстрация не дольше 5 минут.

## 2. Что нужно получить в самом начале

1. Отдельный PDF исходного чек-листа: восемь критериев, веса, типы и шкалы ответов, N/A, грубые ошибки, правила итогового балла и округления. До его получения нельзя объявлять формулу полностью соответствующей кейсу.
2. Скачать DEV по кнопке на странице 3 руководства. Ссылка встроена в PDF. Не переносить подписанную ссылку в публичный репозиторий; адрес подключения задавать конфигурацией.
3. Проверить состав DEV: 65 записей, из них 60 чатов и 5 звонков; 35 RU, 15 KZ, 15 EN. Проверить доступность записей звонков.
4. Уточнить время старта, порядок получения контрольного group_id и канал передачи ссылки на репозиторий. Точное расписание и число команд объявляются отдельно.
5. Выбрать доступную модель и убедиться, что она обрабатывает русский, казахский и английский; проверить ограничения и стоимость на нескольких диалогах.

## 3. Обязательные функции и условия готовности

| Функция | Что реализовать | Как проверить готовность |
|---|---|---|
| Редактор чек-листа | Добавление и изменение критерия, формулировки, веса, типа ответа, разрешения N/A; шкала для числового ответа; сохранение | Новый критерий добавляется через UI и участвует в следующей оценке без правки кода |
| Загрузка диалогов | Получение набора по group_id, выбор диалога и чек-листа | Открываются RU/KZ/EN, чаты и звонки; исходные метки времени сохранены |
| Оценка оператора | Реплики client, bot и system используются как контекст | Поведение бота не засчитывается как действие оператора |
| Результат по критерию | Ответ, баллы, вес, объяснение, доказательство | Для каждого критерия можно понять, почему выставлена оценка |
| Отсутствующее действие | Проверенный участок разговора вместо выдуманной цитаты | По пропущенному действию указан диапазон, где его проверяли |
| N/A | Причина неприменимости, перераспределение веса | Итог считается по применимым критериям согласно исходному чек-листу |
| Итог | Взвешенные шкальные оценки, секции при наличии, отдельная грубая ошибка | Ручной контрольный расчёт совпадает с результатом системы |
| Карточка диалога | Список, транскрипт, оценка, переход к доказательству | Клик открывает нужное сообщение или фрагмент звонка |
| Звук | Прослушивание или переход к плееру | Запись доступна; для интонации и дикции используется звук |
| Апелляция | Выбор критерия, комментарий, сохранение обращения | Проверяющий видит исходный ответ, комментарий и контекст |
| Решение | Подтверждение или изменение оценки с причиной | Сохраняются исходная оценка, решение и финальный результат; итог пересчитан |

Авторизация для демонстрации не нужна. Действия подачи апелляции и проверки должны быть отдельными в интерфейсе.

## 4. Рекомендуемая реализация

Для 24 часов достаточно одного приложения: веб-интерфейс + небольшой сервер + SQLite. Например, JavaScript/TypeScript с React на клиенте и Node.js на сервере. Это выбор команды, а не условие кейса.

Минимальные экраны:
1. Диалоги: язык, канал, статус оценки, выбор записи и запуск обработки.
2. Чек-листы: редактор критериев и сохранение конфигурации.
3. Карточка диалога: транскрипт, плеер, итог, критерии и ссылки на доказательства.
4. Апелляции: спорный критерий, комментарий, исходное доказательство, решение и новый итог.

Разделить обязанности компонентов:
- Адаптер API получает DEV/контрольный набор на сервере; это также решает возможный CORS.
- Модель получает выбранный чек-лист и диалог; возвращает структурированные ответы, причины и идентификаторы доказательств.
- Сервер проверяет допустимость ответа, существование ссылок на сообщения и корректность числовых диапазонов.
- Отдельный детерминированный модуль считает веса, N/A, секции и округление. Не поручать итоговую арифметику модели.
- Хранилище сохраняет диалоги, версии чек-листов, оценки, апелляции и решения.

Версионирование чек-листов рекомендовано: каждая оценка ссылается на сохранённую версию; изменение критерия создаёт новую версию. Старые результаты остаются объяснимыми. Повторная оценка создаёт новый результат.

Предлагаемые сущности: Conversation, Message, ChecklistVersion, Criterion, Evaluation, CriterionResult, Appeal, ReviewDecision. У сообщения должен быть стабильный ID или индекс; исходный timestamp хранится отдельно. Для звонка дополнительно нужна корректная привязка временной отметки к позиции аудио, а не произвольное трактование ISO-времени как секунд.

Транскрипт передаётся модели как анализируемые данные: команды и просьбы внутри разговора не должны менять правила оценки. Это рекомендация по устойчивости решения.

## 5. Как считать оценку

Сначала перенести точные правила из отдельного PDF, затем реализовать их как код и проверить вручную.

Общий принцип из руководства: шкальный результат учитывает вес; N/A исключается из применимых критериев с перераспределением веса; грубая ошибка отмечается отдельно; правила секций и округления берутся из исходного чек-листа.

Условный пример только для понимания перераспределения: при весах 20/30/50, если второй критерий N/A, относительные веса оставшихся составляют 20/70 и 50/70. Это не заменяет формулу организаторов. Влияние грубой ошибки на итог, обработку нулевой суммы весов и случая «всё N/A» нужно определить по чек-листу; не выдавать произвольно 0 или 100.

## 6. План на 24 часа

| Время от старта | Действия | Проверяемый результат |
|---|---|---|
| T+0–1 | Получить чек-лист и DEV, сверить требования, назначить ответственных | Таблица критериев и список обязательных сценариев |
| T+1–3 | Создать каркас, схему данных, импорт, сохранить первый чек-лист | Реальный диалог открывается, конфигурация сохраняется |
| T+3–7 | Реализовать вызов модели, структуру ответа, проверку доказательств, расчёт | Сквозная оценка одного диалога с корректным итогом |
| T+7–11 | Доработать редактор чек-листа, список и карточку, переходы к репликам, звук | Все основные действия доступны в UI |
| T+11–14 | Реализовать апелляцию, решение, историю и пересчёт | Полный сценарий от оценки до финального результата |
| T+14–18 | Проверить RU/KZ/EN, звонки, N/A, шкалы, пропуски и грубые ошибки | Найдены и исправлены существенные ошибки |
| T+18–21 | Проверить замену критерия через UI, устойчивость, README и запуск | Решение запускается по инструкции; новая конфигурация применяется |
| T+21–23 | Подготовить демонстрацию, репетицию, заранее передать ссылку на репозиторий | Защита укладывается в 5 минут; есть резерв времени |
| T+23–24 | Получить контрольные транскрипты, запустить обработку, проверить результаты, зафиксировать коммит | Контрольные данные обработаны; версия для жюри зафиксирована |

После стоп-кода обработка данных и изменение чек-листа через UI разрешены на зафиксированной версии. Изменять код после T+24 для сдаваемого результата нельзя.

Если команда из четырёх человек: один отвечает за интерфейс, второй за сервер/данные/апелляции, третий за модель/доказательства/расчёт, четвёртый за проверку качества/интеграцию/README/защиту. Если людей меньше, сначала завершить сквозной сценарий, затем расширять покрытие. Состав команды руководством не задан.

## 7. Минимум для сдачи и сильное решение

Минимально готовое решение закрывает все обязательные строки из раздела 3 на реальных данных и позволяет выполнить проверку нового критерия через интерфейс. Декоративные экраны без работающих переходов, сохранения и пересчёта не закрывают сценарий.

Сильное решение дополнительно:
- Одинаково объяснимо оценивает RU/KZ/EN; точные доказательства ведут к исходному фрагменту.
- Проходит ручную сверку на небольшой разнородной выборке: три языка, чат и звонок, N/A, пропуск действия, грубая ошибка, спорный ответ. Объём выборки выбирает команда.
- При сбое модели показывает понятную ошибку и допускает повтор; не превращает ошибку обработки в низкий балл оператора.
- Не теряет апелляции и историю после перезапуска; сохраняет различие исходной и финальной оценки.
- Измеряет время и стоимость обработки; для платного API учитывает все вызовы одной оценки.
- Имеет чистый запуск по README и пример конфигурации без ключей и подписанных URL.

Не тратить первые часы на регистрацию, сложную ролевую систему, обучение своей модели, распознавание уже расшифрованных звонков или полноценную интеграцию Dynamics. Они не указаны как обязательные результаты. Если конкретный критерий оценивает дикцию/интонацию, работу со звуком нужно включить в обязательный объём.

## 8. Сценарий защиты — 5 минут

1. 0:00–1:00 — показать интерфейс и выбранный диалог.
2. 1:00–3:00 — открыть оценку, объяснение, переход к реплике, пример N/A и итоговый балл.
3. 3:00–4:00 — подать апелляцию, показать решение проверяющего и новый итог.
4. 4:00–5:00 — изменить критерий, сохранить чек-лист и применить его к диалогу.

До выступления заранее выбрать понятные примеры. Показать хотя бы один реальный сквозной сценарий; резервные скриншоты полезны только как страховка при техническом сбое.

## 9. Чек-лист перед сдачей

- [ ] Все восемь исходных критериев перенесены из отдельного PDF без выдуманных правил.
- [ ] Новый/изменённый критерий работает через UI без изменения кода.
- [ ] DEV импортирован и состав проверен; контрольный group_id меняется настройкой.
- [ ] RU, KZ, EN и оба канала проверены.
- [ ] По каждому критерию есть ответ, баллы, вес, объяснение, доказательство или проверенный участок; у N/A есть причина.
- [ ] Проверены веса, шкалы, перераспределение при N/A, округление, секции при наличии и грубая ошибка.
- [ ] Переходы к сообщениям и записи работают.
- [ ] Апелляция и решение сохраняются; исходная оценка доступна, итог пересчитывается.
- [ ] README проверен запуском; для платной модели указаны название и стоимость полной оценки.
- [ ] Репозиторий открыт, ссылка передана организаторам, секреты не опубликованы.
- [ ] Контрольные данные обработаны; последний коммит зафиксирован до стоп-кода.
- [ ] Защита отрепетирована и занимает не более 5 минут.
